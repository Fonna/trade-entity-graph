# M8 Demo Acceptance Design

## Goal

Build the M8 acceptance package for `trade-entity-graph`: a repeatable demo dataset, pre-seeded review outcomes, and a documented acceptance flow that proves the MVP P0 loop works end to end.

M8 completes the current P0 milestone by moving from "services and UI exist" to "business users can run a realistic demo with about 50 entities, review relationships, inspect evidence, and export results."

## Scope

Included:

- Generate and commit demo source files under `data/demo/`.
- Provide a deterministic generation script so the files can be regenerated.
- Cover about 50 company entities across multiple roles and countries.
- Generate enough orders to produce dense but inspectable relationship evidence.
- Preserve pending relationship candidates for manual review demos.
- Seed a curated subset of reviewed relationships that covers the main final relationship types.
- Add tests that verify the generated demo can run through import, edge generation, claim aggregation, review seeding, graph query, evidence query, and export.
- Add documentation for the M8 acceptance commands and checklist.

Excluded:

- New product UI beyond small copy or documentation updates needed for M8.
- P1 graph features such as two-hop expansion or path search.
- External public-information verification.
- PostgreSQL, Neo4j, BI, CRM, or Lark integration.

## Demo Dataset

The demo dataset will be generated by `scripts/generate_demo_data.py` and committed as generated files in `data/demo/`.

Files:

- `data/demo/demo_entities.csv`
- `data/demo/demo_orders.csv`
- `data/demo/demo_relationship_candidates.csv`
- `data/demo/README.md`

The generator must be deterministic. Running it twice should produce stable row ordering and stable values, so future changes are reviewable in Git diffs.

### Entity Coverage

The dataset should contain about 50 entities. The exact count can be slightly above or below 50 if needed to make the relationship story coherent.

Entity groups:

- Global brand owners and trading customers.
- China and Southeast Asia factories.
- Overseas buyers and consignees.
- Overseas sales centers.
- Group headquarters and subsidiaries.
- Logistics service providers.
- A few noisy or ambiguous entities for review decisions.

Entity fields must match the current importer aliases:

- `canonical_name`
- `original_name`
- `clean_name`
- `alias_name`
- `country`
- `entity_type`

Entity type values should stay simple and readable, for example:

- `group`
- `customer`
- `factory`
- `buyer`
- `sales_center`
- `logistics`
- `trader`
- `unknown`

### Order Coverage

The order file should contain roughly 80-120 rows. This is large enough to produce meaningful confidence scores and repeated relationship evidence, but small enough for a local demo.

Order fields must match the current importer aliases:

- `order_id`
- `customer_name`
- `shipper_name`
- `consignee_name`
- `notify_name`
- `teu`
- `product_name`
- `function_category`
- `destination_country`
- `destination_port`
- `order_date`

The orders should intentionally cover:

- Repeated customer-to-shipper lanes that aggregate into high-confidence candidates.
- Customer-to-consignee and customer-to-notify relationships.
- Shipper-to-consignee supply-chain relationships.
- Multiple destination countries and ports.
- Multiple product categories.
- Some rows with `SAME AS`, `TO ORDER`, or `YQN LOGISTICS` in role fields to prove invalid role filtering remains covered by the demo.
- Some lower-volume relationships that remain pending for manual review.

### Supplemental Candidate File

`demo_relationship_candidates.csv` should represent pre-existing relationship analysis imported from an earlier manual or external process. It is not the primary source of P0 claims, because M4 already aggregates claims from order-role edges.

It should include a small set of supplemental candidates using stable names rather than database IDs:

- `from_canonical_name`
- `to_canonical_name`
- `candidate_relation_type`
- `confidence_level`
- `confidence_score`
- `order_count`
- `total_teu`
- `recommendation_reason`

The current generic relationship importer expects database entity IDs, which are UUID-based and not stable across imports. For M8, `scripts/import_demo_data.py` should import entities and orders through the existing import pipeline, resolve the supplemental candidate file by canonical name after entities exist, and insert those extra candidates into the same demo database.

## Review Seeding

Add `scripts/seed_demo_reviews.py`.

This script runs after:

1. database initialization,
2. demo import,
3. order-role edge generation,
4. relationship-claim aggregation.

It should create a realistic reviewed state while leaving some candidates unreviewed.

Seeded review outcomes:

- Confirm several high-confidence claims as `trading_partner`.
- Modify selected claims into `factory_node`.
- Modify selected claims into `sales_center`.
- Reject selected noisy claims as `rejected_relation`.
- Manually create group relationships such as `same_group` and `subsidiary`.
- Manually create one or more `logistics_service` relationships.
- Leave at least 10 aggregated `relationship_claim` rows with no curated relationship, so Streamlit still has useful pending review work.

Final curated relationship types to cover:

- `same_group`
- `subsidiary`
- `factory_node`
- `sales_center`
- `trading_partner`
- `logistics_service`
- `rejected_relation`

Final curated relationship statuses to cover:

- `verified`
- `rejected`
- `manual_only`

The script should be idempotent enough for demo use. If it detects existing demo review decisions, it should stop with a clear message rather than duplicate curated relationships. This keeps the first M8 version simple and avoids risky delete/update logic.

## Acceptance Flow

The documented M8 flow should show how to run the demo locally:

```powershell
uv --cache-dir .uv-cache run python scripts\generate_demo_data.py
uv --cache-dir .uv-cache run python scripts\init_db.py
uv --cache-dir .uv-cache run python scripts\import_demo_data.py
uv --cache-dir .uv-cache run python scripts\seed_demo_reviews.py
uv --cache-dir .uv-cache run pytest
uv --cache-dir .uv-cache run ruff check .
uv --cache-dir .uv-cache run python scripts\run_ui.py
```

`scripts/import_demo_data.py` should be a thin demo-specific adapter around the existing import pipeline, edge generation, claim aggregation, and supplemental candidate loading. It should not replace the generic importer.

The acceptance checklist should verify:

- Demo files exist and have the expected approximate sizes.
- Import creates one `import_batch` and records archived source files.
- Import creates about 50 entities and many aliases.
- Orders create evidence rows and the four P0 role-edge types.
- Aggregation creates relationship candidates with high, medium, and low confidence levels.
- Seeded reviews create curated relationships and decision/audit rows.
- Rejected relationships are retained but hidden from default graph output.
- A central company graph returns nodes and edges.
- Relationship evidence is queryable.
- Export returns relationship rows for a central company.
- Streamlit can be launched for manual walkthrough.

## Tests

Use TDD during implementation. Add tests before production code.

Primary test file:

- `tests/test_demo_acceptance.py`

Test cases:

- `test_generate_demo_data_writes_importable_files`
  - Runs the generator into `tmp_path`.
  - Verifies entity, order, and candidate files exist.
  - Verifies approximate counts and required columns.

- `test_demo_acceptance_flow_imports_reviews_graphs_and_exports`
  - Generates demo files into `tmp_path`.
  - Imports them into a temporary SQLite database.
  - Generates order-role edges.
  - Aggregates relationship claims.
  - Seeds demo reviews.
  - Verifies entity, evidence, edge, claim, curated relationship, decision, and audit counts.
  - Verifies final relationship type coverage.
  - Verifies pending candidates remain.
  - Verifies graph, relationship evidence, and export services return useful data.

The tests should avoid relying on global `data/` paths. They should call generator functions with explicit output directories and use temporary databases.

## Risks and Constraints

- The current importer depends on column aliases and name matching. Demo files should use English logical column names to avoid encoding issues in tests and diffs.
- The current review service creates curated relationships from claims or manual inputs. It does not deduplicate decisions. The seed script should detect existing seeded review data and stop rather than duplicate.
- The current graph service defaults should continue to hide `rejected` curated relationships. Tests should verify this.
- Existing untracked local Streamlit log files are unrelated to M8 and should not be included in M8 commits.

## Done Criteria

M8 is complete when:

- Demo generation script and generated demo files are committed.
- Review seeding script is committed.
- M8 tests pass.
- Full test suite passes.
- Ruff passes.
- README and task breakdown document the demo acceptance flow.
- The first-version acceptance checklist is updated with evidence from the demo run.
